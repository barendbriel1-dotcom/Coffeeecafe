# Assets App Edits - Permanent Status Approval Workflow

## Overview
This follow-up conversation introduced a new **Permanent** asset status with a stricter approval workflow. The key business rule is that a permanent assignment must begin from the **Sign Out** page, but it must **not** immediately finalize the asset as permanently assigned. Instead, it must create a request inside **Pending Approvals**, where only `barend@encounterchurch.co.za` can approve or reject it.

## Confirmed Workflow Direction

### 1. New Permanent Status
- Added a new asset lifecycle status called **Permanent**.
- This status is visible in shared status helpers, labels, badges, and filters.
- It is intended to represent an item that is permanently assigned to a holder instead of following the normal return cycle.

### 2. Approval Before Permanent Sign-Out Is Final
- The user clarified that **Permanent must still be triggered from the Sign Out page**.
- Choosing **Permanent** during sign-out should **not** immediately complete a permanent assignment.
- Instead, the sign-out action should create a **pending approval request**.
- Only after approval should the asset become truly **permanently signed out** to the selected user.

### 3. Pending Approvals Ownership
- The permanent workflow belongs in the **Pending Approvals** section of the Admin page.
- The user explicitly rejected placing the permanent request workflow in the **Unassigned** section.
- The request and review flow should live alongside the app's existing admin approval patterns.

### 4. Approval Authority
- Only the main user `barend@encounterchurch.co.za` may approve or reject permanent assignment requests.
- This approval is required for:
- The first permanent assignment of an asset.
- Any later transfer or movement of an already permanent asset to another user.

### 5. Enforcement Goal
- Once an item is permanently assigned, it should not move through normal sign-out, handover, or reassignment flows without generating a new approval request.
- The backend should enforce this rule, not only the UI.

## Current Implementation State
- Shared frontend status helpers were updated to include **Permanent**.
- A backend migration was started to add:
- The `permanent` status to the enum.
- A `permanent_asset_requests` approval table.
- Approval RPCs for permanent assignment review.
- The Admin page was updated to surface permanent requests under **Pending Approvals**.
- The workflow still needs to be adjusted so that **the Sign Out page is the true entry point** for creating these permanent requests.

## Next Required Change

- After approval, the asset should become permanently assigned to the chosen user.
